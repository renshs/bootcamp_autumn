# Avito search inference

Финальное решение: multilingual E5-small и USER2-base без LoRA генерируют кандидатов; CatBoost выбирает до 50 объявлений из пула до 1000. Конфигурация, признаки, версия модели и SHA-256 весов зафиксированы в `configs/final.json`.

В Git включены код inference, небольшая модель CatBoost, установщик encoder'ов, зависимости, ноутбук запуска и тесты. Данные, ответы benchmark, экспериментальные результаты и большие веса моделей не включены.

## Как я пришёл к этому варианту

Сначала я проверял простые текстовые и исторические списки. У них не хватало покрытия для новых формулировок, поэтому добавил семантический поиск. E5-small хорошо работал с коротким текстом объявления, в который входят заголовок, параметры услуги и часть описания. USER2-base дал другие полезные кандидаты, особенно когда объявлению требовалось более длинное описание: для него используется окно 512 токенов. Оба encoder'а ищут в полном переданном каталоге; списки объединяются с удалением повторов.

Географию и категорию я использую как мягкие сигналы, а не как обязательные фильтры. В обучающих взаимодействиях встречались выбранные объявления из другой локации, поэтому жёсткий фильтр мог бы их потерять. Для категории запроса 0 поиск идёт по всем категориям. У E5 есть отдельный канал близких локаций, оценённых по координатам объявлений.

Из объединённых списков формируется пул до 1000 кандидатов. CatBoost ранжирует его по 26 признакам: близость и позиция в каждом encoder'е, присутствие кандидата в списках, совпадение категории/локации, расстояние, покрытие слов запроса заголовком и параметрами, длины текстов, рейтинг и число отзывов. Ещё три признака — BM25 для заголовка, исходной строки параметров и описания. Для них статистики считаются по всему входному каталогу, а не по кандидатам; это даёт модели явное лексическое соответствие рядом с семантическим. Параметры BM25 и все признаки зафиксированы в конфигурации.

## Как проверял качество

Для разработки использовал локальный dev из 5000 запросов. Разбиение строилось по группам нормализованного текста, чтобы одинаковые формулировки не попадали одновременно в обучение и dev. Основная метрика — Recall@50 по всем запросам, включая те, у которых нужного объявления не оказалось в пуле. Разницы вариантов оценивались парным bootstrap по текстовым группам. Отдельно смотрел запросы с фильтрами и без, а также цели в точной локации и вне её.

Финальный вариант BM25 с `b=0.25` получил на dev Recall@50 **0,82087**. На прежней контрольной выборке — **0,81939** против **0,81642** у предшествующего варианта. Контроль уже использовался в ходе работы, поэтому это повторная проверка, а не новая независимая оценка. После неё параметры не менялись. Отправленный ответ получил скрытый Recall@50 **0,818220**; это значение сообщено после загрузки на платформу, скрытых меток у меня нет.

## Ошибки, которые повлияли на решение

Самый заметный провал был на объявлениях вне точной локации: ранний географический бонус слишком сильно выталкивал их из top-50. Я уменьшил влияние точной локации для E5 и добавил близкие локации, а в CatBoost оставил расстояние отдельным признаком. Другой случай — запрос с фильтрами, когда нужные слова есть в параметрах или описании, но embedding их сглаживает; для этого добавлены три BM25-признака. Длинные параметры могли вытеснять описание из короткого окна, поэтому для USER2 используется полный исходный текст и окно 512. Наконец, размер кеша embeddings сам по себе не гарантирует правильный порядок объявлений: при чтении кеш сверяется с ID, подготовленными текстами, моделью и её настройками. Эти изменения выбирались на dev; качество для категории 0 без разметки не утверждается.

## Установка

Нужны Python 3.12, CUDA GPU и входные Parquet-файлы.

В WSL Ubuntu:

```bash
uv sync --locked
uv run --locked python scripts/install_model_archives.py --download
export HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1
uv run --locked --offline python -m solution.predict \
  --queries data/benchmark_queries.parquet \
  --items data/benchmark_items.parquet \
  --output answer.csv \
  --config configs/final.json
```

В Windows:

```powershell
python -m pip install -r requirements-final.txt
python scripts/install_model_archives.py --download
$env:KMP_DUPLICATE_LIB_OK='TRUE'
$env:HF_HUB_OFFLINE='1'
$env:TRANSFORMERS_OFFLINE='1'
python -m solution.predict --queries data/benchmark_queries.parquet --items data/benchmark_items.parquet --output answer.csv --config configs/final.json
```

Установщик пробует публичную папку Яндекс Диска и при недоступности скачивает закреплённые ревизии [E5-small](https://huggingface.co/intfloat/multilingual-e5-small/tree/fd1525a9fd15316a2d503bf26ab031a61d056e98) и [USER2-base](https://huggingface.co/deepvk/USER2-base/tree/94bbff0cc696f26dc93b275fc874657727df0c29) с Hugging Face. Загрузку обеих моделей с HF в пустую папку, SHA-256 и открытие через Transformers проверили. Для выбора только HF: `python scripts/install_model_archives.py --download --source huggingface`. Во время inference сеть не используется; отсутствие или изменение файлов моделей вызывает ошибку до обработки данных.

В `queries.parquet` обязательны уникальный строковый `query_id`, `search_query`, `search_location_id`, `search_category`. В `items.parquet` обязательны уникальный строковый `item_id`, `item_category_id`, `item_location_id`. Дополнительные поля описаны в `solution/predict.py`. Выходной CSV имеет колонки `query_id,answer`; в `answer` — до 50 существующих уникальных ID через пробел. Категория запроса 0 ищет по всему корпусу.

Ноутбук `notebooks/reproduce_solution.ipynb` вызывает тот же `solution.predict` и проверяет формат ответа. Проверка кода: `python -m unittest discover -s tests -p 'test_*.py'`.

### Необязательный кеш benchmark

Готовые item embeddings находятся в `artifacts/benchmark_item_cache.zip` (около 416 МиБ), который хранится через Git LFS. После обычного `git clone` с установленным Git LFS архив скачивается автоматически; inference находит его сам. Он содержит по `.npy` и `.json` для E5 и USER2. Если архив скачан отдельно, его можно передать явно:

```text
--cache-dir cache/benchmark --cache-archive /путь/к/benchmark_item_cache.zip
```

Если Git LFS не скачал объект, выполните `git lfs pull`. В таком случае обычный Git оставляет в `artifacts/` только небольшой указатель; inference пересчитает embeddings. По желанию вместо локального ZIP можно указать `--cache-dir cache/benchmark --cache-public-url <ссылка-на-папку-Яндекс-Диска>`. SHA-256 архива `c8fff2b1264347a8d73f417a1c19c75d81f3628b79693b85a688556f25f02bd3` и хеши четырёх файлов заданы в `configs/benchmark_cache.json`. Архив сначала проверяется, затем распаковывается; сами манифесты сверяются с порядком ID, текстами, моделями и настройками входного каталога. Если кеша нет, item embeddings пересчитываются. Неполный или повреждённый кеш вызывает явную ошибку. Кеш подходит только для исходного benchmark-корпуса в том же порядке.

На полном benchmark в исходной Windows-среде код с проверенным кешем объявлений дал CSV, побайтно совпавший с отправленным (SHA-256 `c016e286bb1b7e099de2661a11c7e2ff2338ac25ccfc0c2af46a9c75ee24014b`). В WSL состав top-50 совпал для всех 2452 запросов; у одного запроса четыре ID поменялись местами на позициях 47–50, что не меняет Recall@50. Сам CSV не опубликован вместе с кодом. Полный холодный inference на новой машине не проверен; при запуске без кеша код заново кодирует весь каталог, что требует GPU-памяти и времени.
